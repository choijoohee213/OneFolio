OneFolio API 명세서

계좌별 잔고파일을 받아 자산배분과 종목별 손익을 계산해 돌려주는 백엔드 API.

Base http://localhost:8080 인증 없음 버전 v1

1. 개요

API의 목적과 모든 요청에 공통으로 적용되는 규칙.

API 소개

증권사 앱은 종목별 손익은 잘 보여주지만 "내 전체 자산에서 지수 몇 %, 개별주 몇 %, 현금 몇 %"라는 배분 관점은 보여주지 않는다. 이 API는 증권사에서 내려받은 잔고파일을 받아 그 질문에 답한다.

잔고파일에는 이미 현재가·평가금액·손익·원화환산이 다운로드 시점 기준으로 들어있다. 그래서 별도 시세 API 없이 파일 파싱만으로 계산이 끝난다.

서버는 아무것도 저장하지 않는다. 업로드된 잔고파일과 계산 결과는 응답을 보낸 뒤 폐기된다. 보유종목·평단·잔고는 클라이언트 로컬(IndexedDB)에만 남는다.

2. 시작하기

API를 호출하기까지 필요한 사전 작업과 사용 순서.

사전 작업 — 잔고파일 준비

  1. 증권사 웹에서 계좌를 하나 선택해 잔고파일을 내려받는다.
  2. 계좌를 바꿔가며 보유 계좌 수만큼 반복한다.
계좌마다 따로 받아야 한다. 파일에는 전체 계좌의 자산총액 요약이 모두 들어있지만, 종목 상세는 다운로드 시 선택한 계좌 것만 담긴다. 한 파일만 올리면 나머지 계좌의 종목이 빠진 채로 집계된다.

API 사용 시퀀스

  1. GET /health — 서버가 떠 있는지 확인한다. (선택)
  2. POST /api/portfolio — 준비한 잔고파일을 한 번에 모두 올린다.
  3. 응답의 holdings[].category를 확인한다. 잘못 분류된 종목이 있으면 사용자가 태깅한다.
  4. 태깅 결과를 overrides에 담아 POST /api/portfolio를 다시 호출한다.
  5. POST /api/ocr — 증권 앱 스크린샷에서 보유 종목을 추출한다. (선택, GEMINI_API_KEY 필요)
  6. POST /api/quotes — 이미 아는 종목의 현재가를 새로고침한다. (선택, KIS_APP_KEY/KIS_APP_SECRET 필요)

서버는 상태를 갖지 않으므로 overrides는 매 요청에 함께 보내야 한다. 매핑의 보관은 클라이언트 책임이다.

▶ POST /api/ocr 증권 앱 스크린샷에서 종목 추출 (Gemini Vision)

증권 앱 캡처 이미지를 받아 Gemini 2.5 Flash Vision으로 보유 종목 정보를 추출한다. GEMINI_API_KEY 환경변수가 없으면 이 엔드포인트는 등록되지 않는다.

요청

Content-Type: multipart/form-data

필드타입필수설명
imagefile필수PNG, JPEG, WebP 이미지

응답 200

{
  "holdings": [
    {
      "name": "삼성전자",
      "quantity": 50,
      "currentPrice": 72000,
      "avgBuyPrice": 65000,
      "evalAmount": 3600000,
      "buyAmount": 3250000,
      "profitLoss": 350000,
      "profitRate": 10.77
    }
  ]
}

보이지 않는 필드는 null로 반환된다.

매입금액 buyAmount는 화면에 그 값이 보일 때만 채워진다. 평균매입가에 수량을 곱해 짓지 않는다 — 화면의 평단은 반올림된 값이라 곱하면 원 단위가 어긋난다(예: 271,222 × 9 = 2,440,998, 실제 매입금액 2,441,000).

curl 예시

curl -X POST http://localhost:8080/api/ocr \
  -F "image=@screenshot.png"
▶ POST /api/quotes 이미 아는 종목의 현재가 새로고침 (한국투자증권 Open API)

종목코드 목록을 받아 현재가만 새로고침한다. 수량·평단가는 그대로 두고 프론트에서 evalAmount를 다시 낸다 — 저장된 값은 건드리지 않는다. KIS_APP_KEY/KIS_APP_SECRET 환경변수가 없으면 이 엔드포인트는 등록되지 않는다.

요청

Content-Type: application/json

{"codes": ["005930", "AAPL"]}

응답 200

{
  "quotes": {
    "005930": {"price": 72000, "currency": "KRW", "prevClose": 71300},
    "AAPL": {"price": 227.5, "currency": "USD", "prevClose": 229.1}
  },
  "usdKrw": 1446.2
}

조회에 실패한 종목코드는 quotes에서 빠진다(요청 전체를 실패시키지 않는다). usdKrw는 원화가 아닌 종목이 하나라도 있을 때만 채워진다. prevClose는 전일 종가로, 값이 없으면 생략된다 — 현재가를 상승/하락 색으로 표시하는 기준이다.

curl 예시

curl -X POST http://localhost:8080/api/quotes \
  -H "Content-Type: application/json" \
  -d '{"codes":["005930","AAPL"]}'
▶ POST /api/portfolio 잔고파일 업로드 → 자산배분 집계

잔고파일을 하나 이상 받아 계좌를 통합하고, 종목을 분류하고, 자산배분과 손익을 집계해 돌려준다.

Request Syntax

POST /api/portfolio HTTP/1.1
Host: localhost:8080
Content-Type: multipart/form-data; boundary=----Boundary

------Boundary
Content-Disposition: form-data; name="files"; filename="계좌1.xls"
Content-Type: application/vnd.ms-excel

(파일 내용)
------Boundary
Content-Disposition: form-data; name="overrides"

{"종목명":"카테고리"}
------Boundary
Content-Disposition: form-data; name="manualAccounts"

[{"id":"임의id","name":"저축은행","totalAsset":8000000,"accountNumber":"111-1111-1111-0"}]
------Boundary
Content-Disposition: form-data; name="manualHoldings"

[{"id":"임의id","name":"정기예금","evalAmount":5000000,"accountId":"manualAccounts 항목의 id"}]
------Boundary
Content-Disposition: form-data; name="holdingEdits"

[{"accountNumber":"111111111110","name":"삼성전자","quantity":200,"evalAmount":14000000}]
------Boundary--

Request Header

헤더필수설명
Content-Type 필수 multipart/form-data. boundary 포함. 대부분의 HTTP 클라이언트가 자동으로 붙인다

Request Element

파라미터타입필수설명제약
files file (반복) 선택 잔고파일. 같은 필드명으로 여러 개를 보낸다. 계좌 수만큼 올린다 전체 32MB 이하
manualAccounts·manualHoldings가 있으면 0개도 가능
overrides string (JSON) 선택 자동 분류를 덮어쓸 {"종목명": "카테고리"} 매핑 값은 카테고리 5종 중 하나
manualAccounts string (JSON 배열) 선택 잔고파일 없이 이름·총액만으로 만든 계좌. {"id","name","totalAsset","accountNumber"} 객체 배열 id·name 비어있지 않음
totalAsset > 0
accountNumber는 선택
manualHoldings string (JSON 배열) 선택 잔고파일에 없는, 직접 추가한 종목. {"id","name","evalAmount","accountId"} 객체 배열. quantity·avgBuyPrice·buyAmount·profitLoss·profitRate를 함께 줄 수 있다. buyAmount를 주면 매입금액을 그 값으로 쓰고, 없을 때만 평단×수량으로 낸다 id·name 비어있지 않음
evalAmount > 0
accountId는 선택. 주면 같은 요청의 manualAccounts 항목 id여야 함
holdingEdits string (JSON 배열) 선택 잔고파일 종목의 값을 직접 고친 것. {"accountNumber","name","quantity","avgBuyPrice","evalAmount"} 객체 배열. 계좌번호+종목명으로 대상을 찾아 값을 덮어쓴다 accountNumber·name 비어있지 않음
quantity ≥ 0
생략된 필드는 파일 값 유지
stockMappings string (JSON) 선택 마스터에서 이름으로 찾지 못한 종목을 코드로 매핑. {"종목명": "종목코드"}. 코드가 빈 문자열이면 기타(시세 조회 불가) 처리 코드는 GET /api/stocks로 검색한 값
확장자는 .xls지만 실제 내용은 HTML 문서다. 서버가 알아서 처리하므로 변환할 필요 없다. 같은 파일을 두 번 올려도 종목이 중복되지 않는다. 계좌는 계좌번호로, 종목은 계좌 + 종목명으로 중복을 제거하며 겹치면 나중 파일 값이 이긴다.
files·manualAccounts·manualHoldings 중 적어도 하나는 있어야 한다. 직접 추가한 계좌나 종목만으로도(잔고파일 없이) 호출할 수 있다.
직접 추가하는 자산은 두 층위다.
  • 계좌(manualAccounts) — 잔고파일이 없는 통째 계좌. "저축은행 800만원"처럼 이름과 총액만 있다. 종목을 안 붙이면 전액이 현금성으로 잡힌다.
  • 종목(manualHoldings) — 개별 자산 하나. accountId를 주면 위 계좌에 붙어 그 계좌 총액에서 자기 몫을 떼어 가고, 비우면 계좌 없이 혼자 자기 평가금액만큼 스스로 집계에 잡힌다.
둘 다 id는 호출하는 쪽이 정한다 — 같은 id로 다시 보내면 그 항목을 수정한 것으로, 목록에서 빼고 보내면 삭제한 것으로 취급된다(서버가 상태를 기억하지 않으므로 매 요청은 그 요청에 담긴 목록 전체로 다시 계산한다). 종목의 분류는 manualHoldings 자체에 넣지 않고 overrides에 종목명으로 얹는다 — 그러면 다른 종목과 똑같은 방식으로 분류되어 응답의 holdings에 섞여 나온다.
holdingEdits로 잔고파일 종목의 수량·평가금액·평단을 고칠 수 있다. 계좌번호와 종목명으로 대상을 찾아 지정한 값만 덮어쓴다. 생략한 필드는 파일 값을 그대로 쓴다. 현재가·매입금액·손익·손익률은 고친 값에서 다시 계산된다. 고치기 전 파일 원본은 응답의 holdings[].original에 담겨 온다 — 클라이언트가 이 값으로 "파일이 바뀌었는데 내 수정을 유지할지" 충돌 판단을 할 수 있다.
같은 계좌를 직접 추가해 두고 나중에 그 계좌의 잔고파일을 올리면 파일이 이긴다. manualAccounts에 accountNumber를 적어 두면, 같은 요청의 잔고파일에 그 계좌가 들어 있는지 하이픈을 뗀 숫자로 맞춰본다. 겹치면 파일 쪽이 실제 총액과 종목 상세를 갖고 있으므로 수동 계좌와 거기 붙어 있던 manualHoldings는 응답에서 빠진다. 안 그러면 같은 계좌가 두 줄로 잡혀 자산이 두 번 세어진다.

accountNumber를 비워 두면 맞춰볼 방법이 없어 파일 계좌와 별개로 남는다 — 나중에 잔고파일을 올릴 계좌라면 번호를 적어 두는 편이 낫다. 갈음됐는지는 응답의 accounts에 그 계좌가 있는지로 알 수 있다.
이 API 는 이전 요청을 기억하지 않는다. 계좌를 하나 더 올린다고 앞서 올린 계좌에 더해지지 않는다. 매 요청은 그 요청에 담긴 파일만으로 계산한다. 여러 계좌를 누적해서 보려면 클라이언트가 파일을 들고 있다가 매번 전부 다시 보내야 한다. 어떤 파일을 빼면 어느 계좌가 빠지는지는 sources로 알 수 있다.

Response Element

필드타입설명
coveredAssetnumber종목 상세가 올라온 계좌들의 자산총액 합. 모든 비중의 분모
totalAssetnumber파일에 적힌 전체 계좌 자산총액 합. 올리지 않은 계좌도 포함된다
accountsAccount[]계좌별 총액과 집계 포함 여부
categoriesCategory[]카테고리별 집계. 금액 내림차순
holdingsHolding[]종목별 상세. 평가금액 내림차순
sourcesSource[]보낸 파일이 각각 어느 계좌를 담당했는지. 요청의 파일 순서와 같다
unmatchedstring[]KIS 종목마스터에서 이름으로 찾지 못한 종목명 목록. 없으면 생략. 사용자에게 stockMappings으로 매핑하도록 안내한다
비중의 분모는 coveredAsset이지 totalAsset이 아니다. 잔고파일은 어느 계좌 것을 받아도 전체 계좌 요약을 담고 있어서, 한 계좌만 올리면 totalAsset에는 올리지 않은 계좌까지 들어간다. 그 차액을 현금성으로 잡으면 보유하지도 않은 현금이 생기므로, 집계는 종목이 실제로 올라온 계좌로만 한다. 어느 계좌가 빠졌는지는 accounts[].covered로 알 수 있다. manualAccounts는 상세 종목이 없어도 항상 covered: true다 — 사용자가 총액을 직접 써넣은 것이라 "파일을 더 올려야 아는" 상태가 아니기 때문이다. 계좌 없이 던진 manualHoldings(accountId 생략)는 계좌가 없으니 이 계산에서 아예 빠진다 — 대신 자기 evalAmount만큼 coveredAsset을 스스로 늘려서, 기존 계좌의 현금성을 깎아 먹지 않고 자기 몫의 비중만 새로 차지한다.

5. 부록

분류 동작과 서버 운영에 관한 참고 사항.

분류 우선순위

순위근거결정하는 것
1요청의 overrides전부
2KIS 종목마스터 조회국내/해외, ETF/개별주
3이름 키워드 규칙마스터에 없는 신규 상장 종목 폴백

마스터 조회는 띄어쓰기와 대소문자를 무시한다. 마스터는 "ETF다"까지만 알려주고 무엇을 담았는지는 구분하지 않으므로, 이 갈래만 이름 키워드로 판단한다 — 레버리지·3X → 레버리지·인버스, 국고채·CD금리 → 채권, 나스닥100·S&P500 → 지수 ETF, 나머지는 테마·섹터. 레버리지를 가장 먼저 보므로 국고채10년레버리지는 채권이 아니라 레버리지로 간다. 애매한 종목은 overrides로 잡아준다.

현금성 계산

현금성은 별도로 집계하지 않고 coveredAsset에서 종목 평가금액 합을 뺀 나머지다. 예수금은 잔고파일에 행으로 나오지 않고 자산총액에만 반영되기 때문이다. 외화처럼 취득원가가 없는 행도 종목이 아니라 이쪽으로 들어간다.

분모가 totalAsset이 아닌 이유가 여기 있다. 계좌 하나만 올렸는데 전체 계좌 합에서 빼면 올리지 않은 계좌의 자산이 통째로 현금성이 된다. 계좌 총액을 하나도 모르면(coveredAsset이 0) 현금성 항목 자체를 만들지 않는다.
